## Лабораторна робота №9 — Реалізація та порівняння алгоритмів сортування


Бульбашка на 100000 елементів і пошук секундної межі виконуються довго. Це повний експеримент із заданих умов, а не зависання.

## Реалізація завдань 1–3

- **Бульбашка з прапорцем.** Порівнює сусідні елементи й припиняє роботу, якщо за прохід обмінів не було. Міняє місцями лише строго більші елементи, тому зберігає порядок однакових ключів.
- **Злиття знизу вгору.** Без рекурсії: зливає ділянки довжини 1, 2, 4 тощо. Один буфер створюється перед циклами; копіюються обидва хвости. При рівності першим береться лівий елемент, тому сортування стабільне.
- **Сортування підрахунком.** Узагальнене за типом елемента й отримує `keyOf`, мінімальний та максимальний ключ. Для чисел діапазон [0;60], для перевірки студентів [0;100]. Частоти перетворюються на кінцеві позиції, елементи читаються справа наліво й записуються в буфер: це стабільна версія. Складність O(n+r), додаткова пам'ять O(n+r), де r — ширина діапазону.

Для підрахунку `cmp` не потрібний: алгоритм не порівнює елементи, а індексує частоти за цілим ключем. Він застосовний до вузького відомого діапазону цілих ключів; для довільних рядків без такого відображення не підходить. Фактичні відношення часу злиття до підрахунку для кожного n наведені під таблицею часу.

**Що рахується.** Одне звернення до `cmp` — одне порівняння; запис елемента в основний масив або буфер — одне переміщення. Обмін через локальну змінну дає **2** записи в масив. Оновлення службових частот — не переміщення елемента. У підрахунку тому 0 порівнянь ключів та 2n записів елементів. Лічильники мають тип **long** замість int із шаблону умови: для бульбашки на 100000 елементах можливі понад 2,1 млрд порівнянь і записів, тож int спотворив би результат через переповнення.

## Пояснення таблиць (Завдання 4)

Бульбашка на вже впорядкованому масиві має рівно n−1 порівнянь і 0 записів: перший прохід одразу завершує алгоритм. На випадковому та зворотному вході кількість порівнянь наближається до n(n−1)/2. Три далекі випадкові обміни можуть змусити елемент рухатися вліво багато проходів, тому «майже відсортований» вхід не обов'язково дешевий для бульбашки.

У злиття кількість записів однакова на всіх чотирьох входах: 2n на рівень. Кількість порівнянь не зобов'язана бути однаковою: на впорядкованих ділянках одна половина вичерпується раніше, а її хвіст копіюється без порівнянь. У всіх випадках масштаб залишається O(n log n). Підрахунок не залежить від початкового порядку й має однакові лічильники.

## Стабільність (Завдання 5)

Очікування задані в коді до запуску: бульбашка, злиття, стабільний підрахунок та `OrderBy` — стабільні; `Array.Sort` стабільності не гарантує. У початкових 12 студентів усі бали різні, тому цього набору недостатньо для експерименту. Додано набір зі спільними балами; фактичні результати й контрприклад наведено нижче.

`OrderBy` використовується **тільки як еталон для прямо запитаної таблиці стабільності**. У власних сортуваннях LINQ, `Array.Sort`, `List.Sort`, `Reverse` не використовуються. Стандартне сортування поза ними готує вхід, еталон і початковий порядок прізвищ.

## Висновок (Завдання 6)

1. Фактичне відношення порівнянь бульбашки та злиття на випадкових n=10000 наведено нижче. Воно відрізняється від 376: число n log₂n — асимптотична оцінка, а не точний лічильник злиття. На конкретних даних є повтори 0–60, неповний останній рівень та копіювання хвостів без порівнянь; бульбашка теж може зупинитися до всіх можливих проходів.
2. `Array.Sort(int[])` має спеціалізований шлях для примітивних значень і не викликає наш `Func<int,int,int>` на кожному порівнянні. Крім того, бібліотечний алгоритм працює переважно на місці, а реалізоване злиття виділяє буфер і двічі записує всі елементи на кожному рівні. Це дві конкретні причини різниці часу: диспетчеризація порівнянь і обсяг роботи з пам'яттю, а не загальна фраза «краще оптимізований».
3. Для 100000 записів із цілим ключем 0–300 та обов'язковою стабільністю виберу **стабільне сортування підрахунком**. Діапазон із 301 ключа малий, час O(n+301), відносний порядок однакових ключів зберігається через накопичені частоти й прохід справа наліво. Потрібен додатковий буфер записів, але для такого обсягу це обґрунтований обмін пам'яті на час.

Усі власні сортування перевіряються і на впорядкованість, і на збереження всіх початкових елементів. Класи сортувань, перевірок і замірів зібрано в одному `Program.cs` за зразком попередніх робіт.
