## Лабораторна робота №8 — Алгоритми пошуку та їх порівняння

Виконав: Давидюк Вадим, КН-3/1.

## Запуск

```powershell
dotnet run --project lab8.csproj -c Release
```

Масив містить 100000 студентів: прізвища та групи з лабораторної 6 циклічно повторюються, бали 0–100 генеруються `new Random(5)`. Сортування й усі пошуки порівнюють **лише Score**. X=53, Y=63; відсутній бал=101. Основний запит — останній індекс X; додатковий алгоритм — рекурсивний бінарний пошук.

## Пояснення (Завдання 1–4)

- Відсутній бал 101 найдорожчий для лінійного пошуку: щоб переконатися у відсутності, треба перевірити всі 100000 записів.
- Бінарний пошук може повернути будь-який індекс у блоці однакових балів, а лінійний — перший. Це коректно: порівнюється ключ, а не особа студента.
- Один `Boundary<T>` отримує монотонний предикат. Для нижньої межі це `Score >= 53`, для верхньої — `Score > 53`. Останній індекс X дорівнює `UpperBound - 1`, якщо блок непорожній; кількість дорівнює `UpperBound - LowerBound`.
- Кількість порівнянь пошуку межі залежить від логарифма довжини масиву: на кожному кроці діапазон ділиться навпіл незалежно від ширини блоку однакових значень.
- Предикат «бал кратний 7» немонотонний: істинність знову й знову змінюється. Метод межі для нього не гарантує правильності; фактичний неправильний результат і правильний лінійний наведено нижче.
- Рекурсивний алгоритм ділить ділянку навпіл і має глибину O(log n). Фактичну максимальну глибину по всіх можливих балах наведено в результатах; близько 18 викликів не створює практичної загрози переповнення стека. Базовий виклик на порожній ділянці враховано в глибині, але він не виконує порівняння елементів.

## Чому ламаються чотири копії (Завдання 2)

1. `lo < hi` пропускає останнього кандидата: навіть єдиний елемент `[7]` не перевіряється.
2. `lo = mid` не звужує ділянку `[1,2]` для пошуку 2: `mid=0`, межі знову 0 і 1. Лічильник обриває дослід на сотому кроці, щоб програма завершилася.
3. `(lo + hi) / 2` переповнює `int`, якщо сума індексів більша за 2147483647. Найменша довжина, на якій це взагалі можливо за допустимих індексів, — **1073741825**: останній індекс 1073741824, його подвоєння вже не вміщується в `int`. Це не означає, що кожний пошук на такій довжині зламається; потрібен відповідний шлях до високих індексів. На 100000 елементах сума індексів ≤199998, переповнення немає. Безпечна формула — `lo + (hi - lo) / 2`; великий масив для демонстрації виділяти не потрібно.
4. На невідсортованому масиві знак порівняння не дозволяє відкинути половину даних. Тому частина наявних значень не знаходиться; точне число невдач зі 100 запитів виміряно нижче.

## Висновок (Завдання 6)

1. У таблиці q=1…100 окупності не досягнуто; додатковий експеримент продовжує пошук за цією межею та уточнює її на сітці 1000 запитів. Число набагато більше за лекційні 34: у невідсортованих даних лише 101 різний бал, тому лінійний пошук часто знаходить перший збіг приблизно за 101 перевірку, а не за n/2. Окрім того, час включає витрати сортування, звернення до об'єктів та виклики порівняння; лекційна модель рахує інші операції. Виміряний результат має шум і не є універсальною сталою.
2. Бінарний пошук на впорядкованих даних відповідає на питання «який перший бал не менший за 53?» та «скільки записів мають бал у [53;63]?». Для другого достатньо різниці двох меж. Сама хеш-структура без додаткового сортування, індексу чи повного перебору не надає таких операцій порядку.
3. Якщо дані змінюються після кожного запиту й потрібні перевірки наявності чи доступ за точним ключем, виберу `HashSet` або `Dictionary`: вставлення та пошук мають середню складність O(1), пересортовувати весь масив не треба. Для кількох записів достатньо перебору. Для запитів діапазону потрібна впорядкована структура або інша модель індексування; точний вибір залежить від виду запитів.

Готові пошуки та LINQ не застосовуються. `Search`, `Broken` і `Measurements` логічно розділені класами всередині одного `Program.cs`, за структурою попередніх робіт.
